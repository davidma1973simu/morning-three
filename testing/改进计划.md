## 第 1 批 · P0（发布前必做）

### P0-1　首次解锁「晚间反思」白屏

- **证据**：`A-04-gate.png`；`pageerror: TypeError: Cannot read properties of undefined (reading 'items')`；G-06 失败。
- **位置**：`success.html` `render()` 796–798 行、`viewWhisper()` 821–830 行。
- **根因**：刚解锁的用户必然没有晚间记录，`ks=[]` → `frame(undefined)` → 读 `r.items` 抛错。
- **改法**：
  1. `render()` 里进入 `viewWhisper` 前加判据：`var hasEvening = Object.keys(DB.days).some(k => anyItem(DB.days[k]));`，`hasEvening` 为 false 时**跳过低语页**，直接 `return viewToday()`。
  2. `frame(k)` 内做兜底：`var r = DB.days[k] || { items:[], low:'' };`，`line` 为空时输出 `—`。
  3. 两处都要改：跳过是主修，兜底是防御，避免别处再触发。
- **验收**：新增断言「首次解锁且 `DB.days` 为空 → 页面渲染出今日输入区、零 JS 异常」；三个画像 G-06 全通过；A-04 截图不再是空白页。

### P0-2　19:00 后首次访问被强制收尾浮层锁死

- **证据**：`C-01-first.png`；F-03/04/06/07/08/09、E-04 共 7 条失败。
- **位置**：`index.html` `mustCheck()` 1485 行、`viewToday()` 1162–1166 行、`renderOverlay()` 1489 行。
- **根因**：`mustCheck()` 只看时间阶段，不看用户是否用过；`viewToday()` 在 `late` 阶段走纯只读分支。
- **改法**（取最小改动，不动 unlocked 老用户流程）：
  1. `mustCheck()` 增加冷启动判据：`if(!firstKey()) return false;` —— **从未写过任何一笔的人，晚上首访不弹收尾浮层**。
  2. `viewToday()` 的 `late` 分支同步处理：无历史且今日空白时，仍给一行可写的「今天想推进什么」（或至少补记输入框），而不是纯只读列表 + 「去收个尾」。
  3. `renderOverlay()` 在空白日收尾时也渲染「一句话（可选）」输入框；`ov_seal_empty` 不再是唯一出口。
  4. 已有记录的老用户维持原流程（19:00 只读 + 收尾），避免破坏已验证的归档完整性。
- **验收**：C 画像 20:30 首访 F-03/04/06/07/09、E-04 全部通过；截图出现可输入框；A/B 老用户晚间流程不变（E-01 仍通过）。

### P0-3　导出备份不含晨间清单历史

- **证据**：G-04 三画像全失败（A 有 8 天晨间数据，导出 98 字节 / 0 天 / 无「方案初稿」）。
- **位置**：`success.html` `exportJSON()` 1364–1369 行、`viewData()` 1094 行、导入处理、`d_note` 文案 523 行。
- **根因**：只导出 `DB.days`（晚间记录），没读 `MKEY='morning-three.v1'`。
- **改法**：
  1. 导出 payload 改为统一备份包：
     ```js
     { app:'morning-three', version:1, exportedAt:new Date().toISOString(),
       morning: JSON.parse(localStorage.getItem(MKEY) || '{}'),
       evening: { days:DB.days, unlock:DB.unlock } }
     ```
  2. 文件名改 `morning-three-backup-YYYY-MM-DD.json`（不再叫 success-diary）。
  3. 导入时分别写回 `morning-three.v1` 与 `success-diary.v1`，并 `render()`；旧格式 JSON 要能兼容（检测到无 `morning` 字段时按老格式只恢复 evening，并提示）。
  4. `d_note` 文案改成「导出包含晨间清单与晚间反思的全部记录」。
- **验收**：断言「导出 payload 含 `morning.days` 且含预置词『方案初稿』/『买菜』/『数学卷子』」三画像全通过；导出后清空 localStorage → 导入 → 首页归档记录条数一致。

## 第 2 批 · P1（本版一起修）

### P1-1　统一「那天输入过」判据

- **位置**：`success.html` `mSince()` 393、`mWindow()` 414–425；`index.html` `sdProgress()` 905–918。
- **改法**：抽一个共享语义函数（两文件各自定义同名同逻辑，或抽到公共 js），判据为：
  ```js
  function hasInput(r){
    if(!r) return false;
    if(r.checkin && r.checkin.at) return true;
    if(r.late && r.late.text && String(r.late.text).trim()) return true;
    return !!(r.tasks && r.tasks.some(x => x && x.text && String(x.text).trim()));
  }
  ```
  三个调用点全部替换 `days[k].tasks || days[k].checkin`。`whisperCard()` 已有严格判据，对齐到同一函数。
- **验收**：B 画像 G-02 通过（窗口真实输入 3 天，`winInputs=3`，`inflatedDays=[]`）；门禁页不再出现「5 / 4」。

### P1-2　首页解锁状态由真值计算

- **位置**：`index.html` `sdOpen()` 903、`sdCard()` 1099–1116；`success.html` `unlock()` 437。
- **改法**：`sdCard()` 不再依赖「success.html 有没有写过 `unlock.at`」。把解锁判定抽成与门禁页同源的计算，或在 `sdCard()` 里用 `sdProgress()` 直接判断：`ran>=7 && (inputs>=4 || ran>=10)` 即视为应开，并显示「进入」而非「还差 n/4」。`success.html` 打开时仍负责写标记，但首页不依赖它。
- **验收**：A 画像 G-03 通过；首页不再出现「5/4」这类分子大于分母的数字；达标时文案改为「已经为你敞开」。

### P1-3　数据入口前置

- **位置**：`success.html` `viewGate()`、`viewWall()` 1048/1088 行。
- **改法**：门禁页也放「数据 · 导出 / 导入」入口；更进一步，把入口提到 `index.html` 洞察页底部（与「回顾全部记录」并列），让前 7 天用户随时能备份。首页不加。
- **验收**：G-05 三画像通过；全新用户（零数据）也能到达导出页。

## 第 4 批 · P3（先验证，别直接改）

这一批全是**假设**，不是需求。按用户既有反馈「只有输出没有输入、看不到输入之外的价值」，方向是对的，但必须先做小样本实验。

1. **即时回报**：现在唯一的回报是 650ms 后 1.9 秒消失的「已保存」。先试零成本方案——把「今天写下的这句话」在输入时以更轻的方式即时呈现（不是加卡片），看 7 天回访是否变化。
2. **回响个性化**：三个画像同一天收到完全相同的策展句。不要用历史内容（用户已明确否决「上面提示涉及之前填写的内容」），可考虑按**首次使用天数 / 时段**轮换，而不是按日历全用户同句。
3. **跨设备与提醒**：无账号是隐私优势，别轻易推翻。先验证「导出/导入修好之后，用户是否真的还需要同步」。
4. **画像适配**：**明确不做**。13 岁与 55 岁的低分来自定位错配，不是功能缺失。若要覆盖，应作为独立产品决策，不是本产品迭代。

**统一判据**：任何 P3 改动，先用 10 人 × 14 天小样本，看「第 3 天回访率」是否提升；不提升就砍掉，不留补丁。

## 附：本次测试暴露的流程问题（非产品缺陷）

- 产品有「导出/导入」功能，但入口藏在解锁后的成就墙，导致测试前 7 天完全看不到——**功能存在 ≠ 用户可达**。以后新增能力，先问「新用户第 1 天能不能碰到」。
- 两个页面（index / success）各自实现了一套「输入过」判据，口径不一致。同源 localStorage 下的双页面应用，判定逻辑应抽公共函数，否则必然漂移。
- `smoke-echo-tone.js` 只守了策展库，`lock_hint` 这类首页高频文案没进护栏。护栏要按「所有面向用户开口的句子」设计，不是按模块。

## v34 增补 · 顺延显式化 + 晨间「提交确认」流程（David 截图反馈）

**问题（截图反馈）**：① 自动顺延——昨天没做的自动带今天，导致每天打开是空页，体验差；② 晨间清单的 checkbox 含义不明（用户不需要晨间完成勾选）；③ 要的流程：写好三件事 → 提交确认 → 简单回馈 → 置顶；提交键变「编辑」键，18:00 前可改，18:00 后锁定。

**决策**：边写边自动存保留；「提交」只做确认 + 反馈并切展示态；18:00 前可反复编辑再提交，18:00 后锁定只读（AskUserQuestion 选「边存+确认」）。

**改动**（仅 index.html + sw.js）：
1. 删晨间完成勾选圆框（`toggleDone` 移除，`editRows` 不再生成 `.check`）。
2. 晨间视图机：草稿 → `submitday`（`committed=true` + toast「已记下今天的三件事」）→ 展示态（`readList` + `editday` 键 + 脚注「改到 18:00 前都行」）→ 点编辑重开；≥18:00 只读导流晚间。
3. 顺延显式化：`seal()` 仅 `picks===2`（显式「带到明天」）才 carry；`takeCarry()` 仅今日空白时落地，非空白不自动带。
4. `DAY_EDIT_MAX` 19:00→18:00，全局 19:00→18:00 文案同步。

**验收**：`testing/v34-flow.js` 聚焦实测 **19/19**（晨间提交/编辑/无勾选框、18:00 后锁定、显式顺延、次日仅带显式顺延项）；`audit-run.js` F-09 改为新断言；`index.html` 无残留 `19:00`/`toggleDone`/`tick`。

**发布**：sw.js v33→v34，commit `7071819`，GitHub Pages 已推并验证线上 v34。**WorkBuddy 入口待 David 本轮显式授权覆盖**（上次 v33 授权不继承）。
